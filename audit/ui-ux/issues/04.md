## Problem

Both Inbox triage actions are enhanced forms whose `action` points at `/inbox/submission/<id>?/accept` or `?/dismiss`. After a successful action, SvelteKit navigates to that route, but the submission has just been consumed, so its loader returns 404. The decision is written, yet the user lands on a global "Submission not found" error with no confirmation and no Inbox context.

The queue also stays stale after triaging a submission from its detail page: the consumed row remains visible and clickable, and the summary counts do not match the rendered rows until a reload.

## Affected routes

- `/inbox` at all widths; `/inbox/submission/<id>` when returning to the queue.

## Steps to reproduce

1. Open `/inbox` with a staged submission.
2. Click **Accept** on the row.
3. Wait for the response.
4. Repeat with **Decline → Dismiss submission**.
5. Separately, open a submission detail, click **Triage as issue**, then return to `/inbox`.

## Actual behavior

- Accept/decline writes succeed, then the browser shows `404 · Page not found · Submission not found` with "Try Again" and "Back to Issues" (not Inbox).
- No success message, undo, or return to the queue; search/filter context is lost.
- After triage-as-issue, the consumed submission remains in the queue with live Accept/Decline controls; summary counts disagree with visible rows.
- Reproduced on multiple seeded submissions and a UUID-identified submission.

## Expected behavior

After any triage decision the user stays on `/inbox`, sees the row removed, counts updated, and brief success feedback. A failure keeps the row and shows an inline error. No action is available on a consumed submission.

## Impact

The primary triage workflow completes in the database but ends in an error page every time. Users cannot confirm success or continue triaging without navigating back, and the stale queue can trigger actions on items that no longer exist.

## Suggested direction

Move accept/dismiss actions onto the Inbox route (or an API endpoint) and update the local feed optimistically. At minimum, suppress navigation after success (`navigate: false`) and return to `/inbox` if a redirect is unavoidable. Derive summary counts from the same projected entries as the table, and invalidate the inbox feed when returning from a detail decision.

## Acceptance criteria

- [ ] Accept from `/inbox` leaves the user on `/inbox`, with the row removed and counts updated.
- [ ] Decline → Dismiss behaves identically and records the dismissal.
- [ ] No request to `/inbox/submission/<id>` after a decision.
- [ ] The summary counts always equal the visible queue.
- [ ] A consumed submission cannot be acted on again.
- [ ] Works with JavaScript disabled.

**Priority:** P1 — every triage action ends in an error page.
