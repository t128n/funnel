## Problem

Choosing **Done** in the issue Status select opens the close dialog before any write. If the dialog is cancelled, the issue is unchanged and the header still reads "In progress", but the select keeps the user's "Done" selection because the reactive value did not change and the DOM value is not reset. The same happens in reverse when a closed issue's status change opens the reopen dialog and is cancelled. Choosing the same option again fires no change event, so the dialog cannot be reopened without selecting a different status (which writes it) or reloading.

## Affected routes

- `/issues/demo/funnel/1` (close), `/issues/demo/funnel/5` (reopen).

## Steps to reproduce

1. Open an in-progress issue and set Status to **Done**.
2. Cancel the Close issue dialog.
3. Compare the header ("In progress") with the Status select ("Done").
4. Try choosing Done again.

## Actual behavior

The select and header contradict each other; re-selecting Done does nothing. Closed-issue variant shows header "Closed" and select "In Review". Reload restores the correct value.

## Expected behavior

Cancelling a dialog restores the select to the issue's actual state. Re-selecting the intended status opens the dialog again.

## Impact

The Properties card cannot be trusted, and closing/reopening becomes a two-step workaround or page reload. Selecting another status just to reopen the dialog performs an unintended write.

## Suggested direction

Derive the select's displayed value from the issue model and reset it in the cancel handler, or defer the optimistic value change until the dialog commits. Consider disabling the select while the resolution dialog is open.
