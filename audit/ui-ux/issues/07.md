## Problem

When the current page is one of the overflow destinations (`/day`, `/attention`, `/epics`, `/milestones`, `/issues?assignee=me`), the matching item inside the closed **More** menu carries `aria-current="page"` and `.active`, but the More toggle itself has no active styling or accessible current-page indication. Nothing in the visible navbar shows where the user is.

The same gap makes **My Issues** (`/issues?assignee=me`) render a generic Issues page: the h1, description, document title and breadcrumb all say "Issues", and the primary Issues link is intentionally inactive. The only evidence of the promised view is a filter select.

## Affected routes

- `/day`, `/attention`, `/epics`, `/milestones`, `/issues?assignee=me` at all widths.

## Steps to reproduce

1. Open `/day`. No navbar destination is highlighted.
2. Open `/issues?assignee=me`. Neither Issues nor More is highlighted; the page title is "Issues".
3. Open More and confirm the active item exists only inside the menu.

## Actual behavior

Five destinations are invisible as current locations in the shell; the current-page cue is hidden inside a closed dropdown. My Issues has no page identity.

## Expected behavior

The More toggle shows an active/current treatment whenever one of its items matches, and exposes the destination to assistive technology. `/issues?assignee=me` identifies itself as My Issues with a matching heading, description and document title while keeping the shared table and filters.

## Impact

Wayfinding regresses for every overflow destination, and users arriving from My Issues cannot confirm they are in the promised view.

## Suggested direction

Derive `overflowActive` from `OVERFLOW_NAV` + `isNavActive` and apply it to the More toggle with an accessible name that includes the active item. Derive the page heading/description from `assignee=me`.
