## Problem

The three theme radios on `/settings/appearance` render unchecked regardless of the active theme. With `data-bs-theme="dark"` and a stored Dark choice, all three inputs report `checked === false` on first render and after reload. Clicking a radio checks it and applies the theme, but navigating away and back loses the selection again. The navbar Theme menu simultaneously shows the current choice, so the two surfaces disagree.

## Affected routes

- `/settings/appearance` in light and dark themes.

## Steps to reproduce

1. Set a theme from the navbar and confirm `document.documentElement.dataset.bsTheme`.
2. Open `/settings/appearance`.
3. Inspect the radios with `document.querySelectorAll('input[type=radio]')`.
4. Reload and repeat.

## Actual behavior

`[false, false, false]` on load even though a theme is active. The section meant to answer "which appearance is active?" gives no answer.

## Expected behavior

The radio matching the stored choice is checked on load, survives reload/navigation, and updates immediately when clicked. System is checked when no explicit choice is stored.

## Impact

Users can unknowingly re-apply a theme or think their preference was not saved. The settings page looks unset.

## Suggested direction

Bind the checked state reactively to the theme store rather than relying on a one-time mount update; ensure the Sveltestrap radio reflects the value on re-render and after navigation.

## Acceptance criteria

- [ ] Opening the page with Light, Dark or System stored checks exactly that radio.
- [ ] The check survives reload and navigation between settings sections.
- [ ] Choosing a radio applies and keeps that selection.

**Priority:** P3 — a clear state-display bug with no data loss.
