## Problem

Each issue row is both a focusable `<tr tabindex="0">` with an Enter handler and a real title link. Keyboard users therefore tab twice per issue. The first stop is a table row with no role, no accessible name and no hint that Enter navigates; the second is the correct title link. With 22 issues the list exposed 78 focusable elements, 44 of them from rows.

## Affected routes

- `/issues` (all group and filter states).

## Steps to reproduce

1. Open `/issues` with a keyboard.
2. Tab into the table.
3. Observe two focus stops per row; the first shows a row outline but does not behave like a link.

## Actual behavior

A `<tr>` is focusable without a role or name; screen readers announce it as a row, not a control. Tab count scales at twice the issue count.

## Expected behavior

One tab stop per issue, through the title link. The row may remain clickable for the mouse, but it should not be a separate focus target unless it is a labelled link-like control. Composition A §13 requires a real title link plus row click, not a row-only affordance.

## Impact

Keyboard and switch users traverse the primary list at double length and meet an unlabelled focus target before the real link.

## Suggested direction

Remove `tabindex`/keydown from `<tr>` and keep the click handler plus `cursor: pointer`; the title link provides keyboard and middle-click access. Verify screen-reader output and the visible focus ring.

## Acceptance criteria

- [ ] One tab stop per issue row.
- [ ] Enter/Space on that stop opens the issue and is announced as a link.
- [ ] The focus ring remains visible on the title link.
- [ ] Mouse click anywhere on the row still opens the issue without hijacking text selection.

**Priority:** P2 — core keyboard browsing is twice as long and includes an unlabelled stop.
