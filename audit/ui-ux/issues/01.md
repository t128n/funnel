## Problem

The three-dot menu on a board card is painted underneath the cards that follow it in the same lane. Only the "Move to…" heading and part of the first item are visible; every actionable item is covered by the next card. `elementFromPoint` at each item's centre returns the following card, and the browser refuses pointer clicks because the target is covered. Escape does not close the open menu.

## Affected routes

- `/board` at 1440×900, 768×1024 and 390×844, light and dark.

## Steps to reproduce

1. Open `/board` at 1440×900.
2. Click the `⋯` control on a card (for example FUN-7 in Todo).
3. Try to click "In Review", "Close issue", or any item below the first.
4. Press Escape while the menu is open.

## Actual behavior

The menu is clipped by the lane's scroll container and covered by subsequent cards. Only the first item is partly reachable. Escape leaves the menu open. Assign, block, close, reopen and open-details are unusable by pointer from the board's only action menu.

## Expected behavior

The card menu renders above all lane content and outside the lane's scroll/clipping context. Every item is visible, hit-testable and keyboard reachable. Escape closes the menu and returns focus to the trigger.

## Impact

The board's only per-card action surface is non-functional. A user must open each issue page to perform routine board actions, and keyboard users can focus items they cannot see.

## Suggested direction

Render the menu in a fixed/portal layer anchored to the trigger (or otherwise escape the lane's `overflow`/virtualized stacking context). Add a regression check that every menu item is hit-testable at all three viewports.
