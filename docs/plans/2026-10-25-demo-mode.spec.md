# Native demo mode — spec

Companion to `2026-10-25-demo-mode.md`.

## 1. Gate and entrypoint

Demo mode exists only for `vite dev` (`dev === true` from `$app/env`) and only when
`FUNNEL_DEMO` is truthy (`1`, `true`, `yes`, case-insensitive, trimmed). A production
build ignores the variable entirely: `isDemoMode()` returns `false` whenever `dev` is
false.

`bun run dev:demo` is the supported toggle. It runs `scripts/dev.ts --demo`, which:

- sets `FUNNEL_DEMO=1`;
- defaults `FUNNEL_DB` to `./data/demo.db` and `FUNNEL_UPLOAD_DIR` to
  `./data/demo-uploads` when they are unset;
- defaults `FUNNEL_SECRET` to a clearly-labelled dev-only placeholder when unset;
- starts `bun --bun vite dev` with the inherited environment.

`bun run dev` remains the real-integration path: no seed, no fake session, and the
normal GitHub App onboarding flow. `FUNNEL_DEMO=1 bun run dev` also works when the
operator supplies a demo database path.

## 2. Seed

`seedDemoDatabase()` is synchronous and idempotent. It marks a completed seed with
the row `state_setting["demo.seeded"]`; an existing marker returns
`{ seeded: false }` and leaves the database untouched, so demo edits survive a dev
restart. Deleting the demo database (and its WAL/SHM files) resets it.

A missing GitHub App row is created with a generated RSA key, a fake client id/secret,
installation id `1`, and `baseUrl` from `FUNNEL_URL` or `http://localhost:5173`. An
existing App row is never replaced. The seed writes:

- settings: repositories `demo/funnel` (`FUN`) and `demo/platform` (`PLT`), projects
  `frontend`/`backend`/`docs`/`infra`, intake default `demo/funnel`, four active
  planning maintainers, and the stock sync/board/planning defaults;
- auth: user `demo-user` (`Riley Demo`, `demo@funnel.local`, role `admin`), a GitHub
  account with subject `1001` (matching the mirrored `demo` user), and an unexpired
  session row;
- mirror: two repositories, five people, canonical plus descriptive labels,
  repo-scoped milestones, at least 20 issues covering untriaged, backlog, todo,
  in-progress, in-review, closed, blocked (overdue/today/upcoming), and one epic with
  child refs, with comments and assignees;
- durable state: pending intake submissions, unread notifications for the demo user,
  work notes, current/next-week plan items, issue events for actual-time cards, and
  delay intervals matching the blocked issues;
- a per-viewer work-hours row for the demo user.

No seed path performs a network call. Timestamps are relative to the seed instant
(`Date.now()` unless `now` is supplied) so the board's Done window and Attention
buckets are populated.

## 3. Local GitHub emulation

Every user-facing write in demo mode goes through `demoProvider()`, an object shaped
like the subset of `GitHubProvider` that Funnel uses for issue writes. It is returned
by `forge.userProvider()`, `forge.installationProvider()`, and `forge.appProvider()`;
`forge.getInstallationId()` returns `1`.

The provider reads and writes the same mirror tables as sync:

| Operation | Behaviour |
| :--- | :--- |
| `threads.get` | Hydrates a `Thread` from `mirror_thread`, labels, assignees, milestone. |
| `threads.setLabels` / `addLabels` / `removeLabels` | Replaces mirror labels and re-derives status/impact/urgency/priority/size/blocked/epic caches. |
| `threads.update` | Updates title/body/state/assignees and bumps `updated_at`. |
| `threads.close` | Sets `state=closed`, `stateReason`, `closedAt`. |
| `threads.setMilestone` | Sets or clears `mirror_thread.milestone_number`. |
| `threads.createComment` | Inserts a `mirror_comment` authored by the demo user. |
| `threads.create` | Inserts the next issue number with labels/assignees and returns it. |
| `request("POST", ".../milestones")` | Inserts the next repo milestone and returns its REST payload. |
| `request("GET", ...)` | Serves issues, comments, labels, milestones and repo installation from the mirror; unknown paths throw a 404-shaped error. |

`urlFor()` returns `https://github.com/<owner>/<repo>/issues/<n>` so successful
writes keep an outbound link. The provider never calls `fetch`.

`/api/repos/...` GET passthrough routes therefore answer from the mirror in demo mode.
The mirror-backed feeds, SSE publishing, notifications, work notes, planning, epics
and attachments remain the normal code paths.

## 4. Startup and session wiring

`hooks.server.ts` `init()` runs migrations against `FUNNEL_DB` and calls
`seedDemoDatabase()` when demo mode is on, then resets the config cache. It skips
canonical-label provisioning, the sync worker and nightly reconciliation, since all
three would call GitHub. A seed failure throws so a broken demo is visible.

`handle()` replaces the Better Auth session lookup with `getDemoAuth()` in demo mode,
so every request is the seeded admin. The normal Better Auth handler still mounts for
`/api/auth/*`; sign-out cannot end the demo session because the next request restores
it. The first-run onboarding gate never redirects because the fake App exists.

`getUserAccessToken()` returns `demo-token` in demo mode.
`scheduleRefresh()` is a no-op in demo mode, since the provider has already written the
mirror and a refresh would call GitHub.

## 5. Documentation and guards

Update the development how-to with the toggle, seed contents, the reset procedure, and
the real-integration alternative (`bun run dev`). Update the CLI reference's
package-script table. Add a commented `FUNNEL_DEMO` block to `.env.example` stating it
is dev-only and ignored by production builds.

Guard with tests:

- `demoModeEnabled` truth table and the `dev` gate;
- seed idempotency and the presence of every view's data;
- provider read/write round trips for labels, comments, create, close and milestone;
- demo token and refresh no-op in demo, real path when off;
- docs mention `bun run dev:demo`, `data/demo.db`, and the `--demo` flag.

## 6. Non-goals

No `--demo` flag on the packaged executable, no production demo mode, no seeded
attachment binaries, no fake GitHub web pages, no live sync, and no changes to Better
Auth's schema or cookie format.
