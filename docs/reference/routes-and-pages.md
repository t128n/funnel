# Routes and pages

Funnel's routes divide into public intake and health endpoints, a first-run onboarding wizard, a login route, authenticated cockpit pages with docked detail panes, role-gated settings sections, and API endpoints.

## Access control

### First-run gate

`src/hooks.server.ts` resolves the Better Auth session on every request. While no GitHub App exists there is no auth instance, and every path outside the exempt set is redirected with `303` to `/onboarding`:

| Exempt path | Reason |
| :--- | :--- |
| `/onboarding` and `/onboarding/*` | The wizard itself. |
| `/healthz`, `/readyz` | Process supervisors and load balancers probe a fresh instance. |
| `/_app` and `/_app/*` | SvelteKit's own bundle. |
| `/api/auth` and `/api/auth/*` | The auth handler answers `503` while unconfigured instead of serving the wizard. |
| A path whose last segment contains a dot | Asset-looking paths. |

Once an App exists, the gate disappears and the normal route guards apply.

### Session and role guards

- `requireUser` redirects an unauthenticated visitor to `/login?redirectTo=<path+query>` with `303`.
- `requireRole` returns `403` for an authenticated visitor below the minimum role.
- `requireAdmin` is `requireRole(..., "admin")`.
- Every `(app)` page load runs the layout guard in `src/routes/(app)/+layout.server.ts`, which calls `requireUser`. The baseline minimum for every cockpit page is therefore `read`; individual layouts add stricter roles.
- The settings layout enforces the section role. Only `/settings`, `/settings/appearance` and `/settings/features` are personal (`read`); every other `/settings/*` path requires `admin`, including direct URL entry.
- Form actions re-check the session and role because SvelteKit layout loads do not run for actions. The shared settings action returns `401` without a session and `403` without `admin`.
- Public routes are `/`, `/intake`, `/login`, `/onboarding/*`, `/healthz`, `/readyz`, `/api/intake` and `/api/auth/*`. Of these, `/healthz`, `/readyz`, `/onboarding/*` and `/api/auth/*` are also first-run-gate exemptions; the others become reachable once an App exists.

The onboarding wizard is additionally gated by `FUNNEL_ONBOARDING_TOKEN` when that variable is set. The token is supplied as `?token=…`, stored in the HttpOnly `funnel_onboarding_token` cookie for one hour, and required by the manifest, callback, install and installed steps. When the variable is unset the wizard is open to anyone who can reach the fresh instance.

The `s=1` query marker means the URL was generated by the page itself and is not presented as a shared link.

### Issue filters and sorting

The issue lists share one URL filter model: `repo`, `state`, `status`, `assignee`, `priority`, `size`, `label`, `planned` and `milestone` repeat (or comma-join) to OR values inside a dimension, while dimensions AND together. `q` carries the search term. Unknown values are ignored. `blocked=true` and `blocked=false` filter on the mirrored blocked cache, so they work with any configured reserved-label prefix. `waiting=true` and `waiting=false` filter on Funnel's local waiting table (`state_issue_waiting`), independent of the blocked flag and any label prefix.

`assignee=none` selects issues with no assignees. It may be combined with named assignees (`?assignee=none&assignee=octocat`), in which case either condition matches. `assignee=me` resolves to the signed-in viewer.

### Search (`q`)

`q` searches issue titles, bodies and every mirrored comment through the FTS5 index. Plain words are prefix-matched and ANDed; FTS operators in user input are quoted, not executed. The term keeps the shared URL model, so it combines with the filter dimensions and survives reloads and shared links.

`q` also accepts issue identifiers and GitHub-style qualifiers:

| Form | Meaning |
| :--- | :--- |
| `#123` | Issue number 123 in any mirrored repo. |
| `FIT-123` | Issue 123 in the repo whose configured shortcode is `FIT` (see `/settings/repositories`). Unknown shortcodes remain plain text. |
| `owner/repo#123` | Issue 123 in that repo. An unknown repo matches nothing. |
| `is:unassigned` | Issues with no assignee. |
| `is:blocked` | Issues with the mirrored `blocked` flag. |
| `label:bug` | Requires the label. Repeat the qualifier to require several labels. |
| `repo:owner/name` | Narrows to that repo. |
| `status:todo` | Narrows to that canonical status (or `status:none` for untriaged). |
| `assignee:login` | Narrows to that assignee; `assignee:me` and `assignee:none` work like the URL dimension. |

Qualifiers are constraining: they AND with the URL dimensions and with each other (labels AND across repeated tokens; repos, statuses and assignees OR inside their own group). A qualifier can therefore only narrow the current result set — `?q=repo:orgA/web&repo=orgA/core` returns nothing rather than both repos. Identifiers and qualifiers are removed from the FTS text; a query may mix them with words (`?q=%231%20crash`). Search results keep the selected sort; relevance ranking is not a separate sort yet.

`/issues` also accepts `sort=priority|updated|created|title` and `direction=asc|desc`. The default is `sort=priority&direction=asc`, which keeps priority rank ascending (P1 first, unprioritized last) and resolves ties by most recently updated. Title sorting is case-insensitive. Both parameters live in the URL, so the chosen sort survives reloads and shared links. Sort is a view preference: it does not count towards the active-filter badge. Board lanes keep their fixed priority order regardless of these parameters.

### Saved views

Issues and Inbox share one saved-view API and a compact **Views** switcher in each toolbar. A saved view is a named preset for the current scope: it stores the URL query string, sort, direction and client grouping, and clicking it navigates to `/{scope}?{query}` and applies the group. The URL remains the runtime source of truth; changing a filter does not update a saved view unless the reader explicitly refreshes it.

- **Personal** views are visible only to their owner. **Shared** views are readable by every signed-in user but editable only by their owner (or an admin, for shared rows).
- Owners can rename, change sharing, pin, refresh a view from the current filters, or delete it. Read-only (`read`) users can open views but get no create/edit/delete controls; the API also rejects their mutations.
- Issues, Inbox and every other cockpit page receive the visible view list from the `(app)` layout. The switcher filters it by the current scope, so Issues never offers an Inbox preset (and vice versa).
- The stored query is constrained to filter keys plus Inbox `snoozed`; it cannot contain a path, fragment or unknown parameter. `sort`/`direction` live in their own columns so reopening a view applies the saved order even when the previous URL had a different one.

### Inbox triage actions

The submission detail route defines three SvelteKit form actions:

| Action | Effect | Token |
| :--- | :--- | :--- |
| `accept` | Creates a GitHub issue in the selected repo (or `intake.default_repo`), with the default `backlog` status and a provenance footer, then deletes the staged row. | Signed-in user's GitHub token. |
| `dismiss` | Hard-deletes the staged row without contacting GitHub. | None; a `write` session is sufficient. |
| `duplicate` | Posts the submission text as a comment on a mirrored issue, then deletes the staged row. | Signed-in user's GitHub token. |

All three require `write`. Accept and duplicate fail with `401` when no user token can be resolved; missing or invalid form fields return `400`; a missing submission or mirror target returns `404`; GitHub failures use the mutation layer's status.

### Settings actions

`/settings/repositories`, `/settings/projects`, `/settings/intake`, `/settings/board`, `/settings/notifications`, `/settings/sync`, `/settings/session` and `/settings/planning` all use `saveSettingsAction`: a JSON `payload` form field is merged onto current settings, validated as one configuration, persisted in a transaction, and propagated through the `settings` SSE event and a sync-scheduler wake-up. Errors return `400` with a `message` and, for per-key validation failures, an `issues` array.

`/settings/sync` also defines a `sync` action. It re-checks the admin role, awaits one `syncAllRepos` pass, and returns `{ synced, repos }` on success or `502` with a `syncError` when one or more repositories failed. The page invalidates its load after either outcome so the health table reflects the cycle's timestamps and degraded flags.

`/settings/people` returns `400` for an invalid role, `404` for an unknown user, `409` when demoting the last administrator, `503` when auth is unconfigured and `502` when the auth provider rejects the change.

## Detail routes

The four cockpit views own self-describing detail paths:

```text
/issues/{owner}/{repo}/{number}
/board/{owner}/{repo}/{number}
/matrix/{owner}/{repo}/{number}
/inbox/{owner}/{repo}/{number}
/inbox/submission/{id}
```

The issue detail load functions validate that `owner`, `repo` and a positive integer `number` are present; a malformed link raises a real `404`. A syntactically valid but not-yet-mirrored issue is left to the Inspector's own empty state. The Inspector fetches `/api/mirror/issues/{owner}/{repo}/{number}` after load, so the detail route itself carries no issue payload.

## Error handling

- `src/routes/+error.svelte` renders every 4xx/5xx, including unknown page routes, with status-specific copy.
- `handleError` in `src/hooks.server.ts` logs unexpected errors with a per-request correlation id. Unhandled 5xx responses expose only generic copy plus that id (`Reference: …`); expected 4xx errors keep their status and message.
- Unknown `/api/*` paths always receive the JSON fallback `404 {"message":"Not found"}` rather than the HTML error page.
- Responses carry `X-Robots-Tag: noindex, nofollow`.
