# Routes and pages

Funnel's routes divide into public intake and health endpoints, a first-run onboarding wizard, a login route, authenticated cockpit pages with docked detail panes, role-gated settings sections, and API endpoints.

## Access control

### First-run gate

`src/hooks.server.ts` resolves the Better Auth session on every request. While no GitHub App exists there is no auth instance, and every path outside the exempt set is redirected with `303` to `/onboarding`:

| Exempt path | Reason |
| :--- | :--- |
| `/onboarding` and `/onboarding/*` | The wizard itself. |
| `/healthz`, `/readyz` | Process supervisors and load balancers probe a fresh instance. |
| `/_app` and `/_app/*` | SvelteKit's own bundle. |
| `/api/auth` and `/api/auth/*` | The auth handler answers `503` while unconfigured instead of serving the wizard. |
| A path whose last segment contains a dot | Asset-looking paths. |

Once an App exists, the gate disappears and the normal route guards apply.

### Session and role guards

- `requireUser` redirects an unauthenticated visitor to `/login?redirectTo=<path+query>` with `303`.
- `requireRole` returns `403` for an authenticated visitor below the minimum role.
- `requireAdmin` is `requireRole(..., "admin")`.
- Every `(app)` page load runs the layout guard in `src/routes/(app)/+layout.server.ts`, which calls `requireUser`. The baseline minimum for every cockpit page is therefore `read`; individual layouts add stricter roles.
- The settings layout enforces the section role. Only `/settings`, `/settings/appearance`, `/settings/features` and `/settings/availability` are personal (`read`); every other `/settings/*` path requires `admin`, including direct URL entry.
- Form actions re-check the session and role because SvelteKit layout loads do not run for actions. The shared settings action returns `401` without a session and `403` without `admin`.
- Public routes are `/`, `/intake`, `/login`, `/onboarding/*`, `/healthz`, `/readyz`, `/api/intake` and `/api/auth/*`. Of these, `/healthz`, `/readyz`, `/onboarding/*` and `/api/auth/*` are also first-run-gate exemptions; the others become reachable once an App exists.

The onboarding wizard is additionally gated by `FUNNEL_ONBOARDING_TOKEN` when that variable is set. The token is supplied as `?token=…`, stored in the HttpOnly `funnel_onboarding_token` cookie for one hour, and required by the manifest, callback, install and installed steps. When the variable is unset the wizard is open to anyone who can reach the fresh instance.

## Public and first-run routes

| Route | Methods | Purpose | Access |
| :--- | :--- | :--- | :--- |
| `/` | GET | Entry redirect once configured: signed-in visitors go to `/inbox`, everyone else to `/intake` (`307`). On a fresh instance the first-run gate redirects to `/onboarding`. | Public. |
| `/intake` | GET, POST | Public submission form. GET renders a prefilled draft from `title`, `body` and `source`, or from the compact `?d=base64url(deflate-raw(json))` deeplink. POST stages a submission and publishes an `intake` event with action `staged`. | Public. |
| `/login` | GET | GitHub sign-in page. An already signed-in visitor is redirected to a safe same-origin `redirectTo` target, or `/inbox`. | Public. |
| `/onboarding` | GET | Manifest-flow wizard, stage 1. Redirects to `/login` once App credentials exist. Renders a token prompt when the onboarding token is required. | Public, or onboarding token. |
| `/onboarding/manifest` | POST | Validates the App name and owner, stores a CSRF state cookie, and returns a self-submitting HTML form that hands the App manifest to GitHub. | Onboarding access; redirects to `/login` if credentials already exist. |
| `/onboarding/callback` | GET | GitHub's manifest redirect. Validates the state cookie, exchanges the temporary code for App credentials, persists them encrypted, resets derived caches and redirects to `/onboarding/install`. Failures redirect to `/onboarding?error=state` or `?error=exchange`. | Onboarding access. |
| `/onboarding/install` | GET | Stage 2: presents the GitHub App installation URL. Redirects to `/onboarding` when no credentials exist. | Onboarding access. |
| `/onboarding/installed` | GET, POST | Stage 3: captures `installation_id` (or the single available installation), lists the installation's repositories, and saves the selected `owner/name` repositories before redirecting to `/login`. | Onboarding access. |
| `/healthz` | GET | Liveness probe. | Public. |
| `/readyz` | GET | Readiness probe. | Public. |

The intake form validates a non-empty title of at most 256 characters and a body of at most `INTAKE_BODY_MAX` characters. Failures return `400` with the submitted fields and an `error` message. The `s=1` query marker means the URL was generated by the page itself and is not presented as a shared link.

### Inbox triage actions

The submission detail route defines three SvelteKit form actions:

| Action | Effect | Token |
| :--- | :--- | :--- |
| `accept` | Creates a GitHub issue in the selected repo (or `intake.default_repo`), with the default `backlog` status and a provenance footer, then deletes the staged row. | Signed-in user's GitHub token. |
| `dismiss` | Hard-deletes the staged row without contacting GitHub. | None; a `write` session is sufficient. |
| `duplicate` | Posts the submission text as a comment on a mirrored issue, then deletes the staged row. | Signed-in user's GitHub token. |

All three require `write`. Accept and duplicate fail with `401` when no user token can be resolved; missing or invalid form fields return `400`; a missing submission or mirror target returns `404`; GitHub failures use the mutation layer's status.

### Settings actions

`/settings/repositories`, `/settings/projects`, `/settings/intake`, `/settings/board`, `/settings/notifications`, `/settings/sync`, `/settings/session` and `/settings/planning` all use `saveSettingsAction`: a JSON `payload` form field is merged onto current settings, validated as one configuration, persisted in a transaction, and propagated through the `settings` SSE event and a sync-scheduler wake-up. Errors return `400` with a `message` and, for per-key validation failures, an `issues` array.

`/settings/availability` is the personal exception. It does not use `saveSettingsAction`; it calls `PUT /api/me/availability` and the calendar-feed routes, which require a session but no `write` role, and it changes only the signed-in viewer's rows.

`/settings/people` returns `400` for an invalid role, `404` for an unknown user, `409` when demoting the last administrator, `503` when auth is unconfigured and `502` when the auth provider rejects the change.

## Detail routes

The four cockpit views own self-describing detail paths:

```text
/issues/{owner}/{repo}/{number}
/board/{owner}/{repo}/{number}
/matrix/{owner}/{repo}/{number}
/inbox/{owner}/{repo}/{number}
/inbox/submission/{id}
```

The issue detail load functions validate that `owner`, `repo` and a positive integer `number` are present; a malformed link raises a real `404`. A syntactically valid but not-yet-mirrored issue is left to the Inspector's own empty state. The Inspector fetches `/api/mirror/issues/{owner}/{repo}/{number}` after load, so the detail route itself carries no issue payload.

## Error handling

- `src/routes/+error.svelte` renders every 4xx/5xx, including unknown page routes, with status-specific copy.
- `handleError` in `src/hooks.server.ts` logs unexpected errors with a per-request correlation id. Unhandled 5xx responses expose only generic copy plus that id (`Reference: …`); expected 4xx errors keep their status and message.
- Unknown `/api/*` paths always receive the JSON fallback `404 {"message":"Not found"}` rather than the HTML error page.
- Responses carry `X-Robots-Tag: noindex, nofollow`.
